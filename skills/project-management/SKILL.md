## 0. このスキルの役割

本スキルは「プロジェクト管理して」と言われたときに、何をどの順で確認し、どう報告するかを定める。

### スキル昇格原則

ルーチン化可能な手順（繰り返し発生し、毎回同じチェックが必要なもの）は、ルール記述ではなくスキルとして登録する。

**判定基準**:
- 同じチェックが3回以上発生している → スキル候補
- 「読んだか」「確認したか」の自己申告でチェックしている → スキル昇格を検討
- ルール違反が繰り返し発生する → スキル化を検討

### スキル新設時の影響範囲チェックリスト

スキルの新設・構造変更・削除を伴う作業では、SKILL.md 本体だけでなく以下の全てが影響する。

| # | ファイル | 確認・更新する内容 |
|---|---|---|
| 1 | `skills/{name}/SKILL.md` | 本体の作成・更新 |
| 2 | `docs/README.md` | スキル一覧やタスク別ロードテーブルの更新 |
| 3 | `CLAUDE.md` | 該当すれば追加 |

### 他スキルとの棲み分け

| スキル | 責務 | タイミング |
|---|---|---|
| **本スキル** | 現状把握・棚卸し・報告 + 教訓記録ルール | オンデマンド |
| doc-management | Memory/README/SKILL の肥大化整理 | スパデートリガー時 |

## 1. PM チェック手順

「プロジェクト管理して」と言われたら、以下を順に実行する。

### Step 1: 状態ファイル読み直し

プロジェクトの state.md や管理用ファイルがあれば読み直す。

確認項目:
- Git テーブル（HEAD SHA, dirty, remote sync）
- 作業中・投入待ちの件数と内容
- 外部エージェント待ち

### Step 2: backlog 読み直し

backlog があれば読み直す。

確認項目:
- 依存関係図が最新か
- チェック待ち一覧
- 投入待ち/作業中の整合

### Step 3: inbox 棚卸し

```
ls .cache/inbox/
```

確認項目:
- 残存指示書の状態（対応 Issue が open か？作業中か？）
- 2週間以上未投入の指示書 → stale 候補としてフラグ
- archive 候補の特定

### Step 4: active/ 棚卸し

```
ls .cache/active/
```

確認項目:
- TASK ファイルの関連 Issue が CLOSED なのに残っていないか

### Step 5: CLI 状況の整理

作業中・投入待ちセクションから:
- 件数
- 各指示書の状態（実行中/待機/完了報告待ち）
- ブロック解除の連鎖

### Step 6: 判断待ち一覧

backlog + active + state から、オーナーの判断/確認が必要なものを集約。

### Step 7: 教訓候補の棚卸し

教訓 INDEX があれば読み直す。
- open 状態の教訓で infusion 可能なものがないか
- セッション中に記録すべき教訓候補が未記録でないか

### Step 8: 報告

上記を構造化して報告する。フォーマット:

```
**プロジェクト管理レポート**

**進行中の作業（N件）:**
| 優先度 | Issue | 状態 | 次のアクション |
|---|---|---|---|

**ブロック解除の連鎖:**
- ...

**通常タスク（N件）:**
- ...

**判断待ち（N件）:**
- ...

**inbox 棚卸し候補:**
- ...

**把握漏れチェック:** state・backlog・inbox の3点整合結果
```

## 2. 教訓記録ルール

### トリガー条件

以下のいずれかを検知したとき:
- 予期せぬ失敗（手順違反、ツールエラー、誤判断）
- ルールの不備・欠落の発見
- 新しい回避策・ベストプラクティスの確立
- 「次回こうすればよかった」と思う状況

### 即記録義務

**検知した同一ターンで教訓 INDEX に追記する。「次ターンで」の猶予は設けない。**

手順:
1. INDEX を読む
2. 最新の LL-{NNN} 番号を確認
3. 新行を追記
4. **Issue 同時起票**: infusion 作業用の Issue を同一ターンで起票し、backlog にも追加する
5. 応答に「LL-{NNN} 記録済み / Issue #NNN 起票済み」と報告

### フォーマット

```
| LL-{NNN} | {YYYY-MM-DD} | {1行要約} | {infusion先ファイル名 or Issue番号} | open |
```

### infusion（ルール反映）

- **タイミング**: 対応 Issue の CLOSED 時（主経路）
- **手順**: Issue CLOSED を確認 → 該当ルールファイルへの反映を検証 → INDEX の状態を `infused` に変更

### INDEX 管理

- 50行以下を目標（doc-management SKILL のスパデートリガー）
- infused 済みで3ヶ月以上経過したものは剪定候補
