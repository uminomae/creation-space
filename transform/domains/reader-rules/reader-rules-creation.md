## §2 creation が記述するもの

5段階モデルは「創造プロセス」のモデルではない。**存在そのものの創造**を記述している。

量子から宇宙まで、物質も現象も、物も心も、精神も含めて全てに適用されるという仮説である。物理的/生命的/心的個体化の区別はスペクトラム上のラベルにすぎない（S55）。

creation が生成する文書は、この仮説を各audienceに向けて報告するものである。具体的には、異なるラベル（先行研究、各学問領域）が同じものを指しているか、見落としはないかを分析した調査の報告である。

30領域の個別調査結果は、ドメインレポートとして別途公開する。guides / survey / academic いずれの出力も、読者がこの個別レポートにたどり着ける参照を含めること。参照先URLは出力時点の公開状態に依存する（NL-017）。

## §3 5段階の扱い

### 定義の参照

5段階（場→波→縁→渦→束）の定義の原型は kesson-driven-thinking の `base/` にある。共通基盤がコンテンツとして定義を持つと正本との二重管理になるため、ここでは扱いのルールのみ定める。

### 導入の仕方

各audience版は導入の仕方を変えてよい:
- general: 体験的に導入してから名前を出す
- designer: 構造として提示しつつ体験的入口を持つ
- academic: 学術的定義として導入し先行モデルと比較する
- report: 定義的・報告的に提示する

### 均等記述の義務（NL-003）

5段階を均等に記述する。渦・束の説明放棄を禁止する。

場→波→縁は体験的に描写しやすく、縁は理論の核心であるため記述が厚くなりがちだが、渦と束を「あるとき起きる」「方向が定まる」で済ませてはならない。各段階に同程度の構造記述を与える。

### 縁の位置づけ（S57）

「縁」は構造類似の判別力が最も高い。境界・際に止まることが創造の本質である。ただし、縁偏重で他の段階を薄くしてはならない。

### スケールの非限定（S55）

5段階のスケールを限定しない。「M2の射程を超える」「このスケールでは適用できない」と書かない。5段階は「創造プロセスモデル」ではなく「存在そのものの創造」を記述している。物理的/生命的/心的個体化の区別はスペクトラム上のラベルにすぎない。

## §4 使わないもの（全版共通）

| 除外対象 | 理由 |
|---------|------|
| [P][M][S]タグ | 内部作業用。読者に見せない |
| Layer番号 | 内部構造。読者向けには温度表現で代替 |
| 生成元パス、内部ファイルパス | 内部管理情報 |
| AI作業環境（フリーズ対策、セッション管理、state.md等） | 読者の関心外（NL-002） |
| commit数、バージョン番号の推移 | 内部管理情報 |
| ツール使い分け（Claude / ChatGPT / Codex） | 本文では不要。方法論として言及する場合は脚注 |
| プレースホルダー（「ここに」「TODO」「TBD」） | 公開前に必ず除去 |
| 「コピペです」等の品質放棄宣言 | 読者への不敬 |

### audience版で上書き可能なもの

以下は audience 版が明示的に許可する場合のみ使用可:
- スピノル（academic版: 付録で許可）

- 先行研究の人名（academic版: 使用可。designer版: ブリッジとして使用可）
- 数理表現（academic版: 付録で使用可）

## §5 温度表現の枠組み

全版共通の枠組み。具体的な割合は各audience版で定義する。

| 温度 | 表現パターン | 使用場面 |
|------|-------------|----------|
| **確定** | 「〜である」「〜が確認された」 | 5段階の定義、調査で繰り返し確認された事実 |
| **有力** | 「〜と考えられる」「〜を示唆する」「〜のように見える」 | 複数領域で一貫した傾向、構造比較の知見 |
| **仮説** | 「仮説として〜が考えられる」「〜かもしれない」 | 単一領域の知見、検証途上の接続 |
| **未解決** | 「〜は未解決である」「〜については保持論点として残す」 | 対立する解釈が残るもの、保持論点 |

### 禁止

- 「〜かもしれません」の3回以上連続使用（全体が不確かに見える）
- 確定事実を「〜かもしれない」で弱める
- 仮説を「〜である」で断定する

## §6 投影スイッチ回避（共通枠組み）

全版に共通する禁止パターン。各audience版が固有の追加パターンを定義する。

| 禁止パターン | 理由 |
|-------------|------|
| 普遍化（「あらゆる創造に〜」「全ての人が〜」） | 射程は広いが、断定は仮説の温度を壊す |
| 効果の約束（「これを使えば〜」「5段階を適用すれば〜」） | ツール売りの圧 |
| 先行研究への攻撃（「〜のモデルは不十分」「〜は古い」） | 指月的記述（S04）。指の優劣ではなく、同じ月を指しているかを見る |
| メタ理論の僭越（「本モデルが既存理論を統合する」） | 包摂を目指すが（S12）、統合を主張しない |

## §6.5 方法論的開示義務（S60）

先行研究との構造対応は、原著の行間を含む解釈行為である。5段階のラベル（場・波・縁・渦・束）はグラデーション上の便宜的な区切りであり、先行研究のラベルも同様である。この対応作業の多くをAIが担っているが、著者（pjdhiro）の解釈とAIの解釈にはずれが生じうる。

**全ての公開出力に以下を含めること:**

- 先行研究との対応は解釈仮説であり、原著の精読に基づく確定的対応ではない
- ラベルの対応にはグラデーションがあり、1対1の厳密なマッピングではない
- AIによる解釈代行のプロセスを含むため、著者自身の精読による検証が完了していない箇所がある

これは個々の主張の温度（確定/有力/仮説/未解決）とは別の次元の開示である。方法論全体の温度。

**配置**: 各audience版が適切な場所に埋め込む。report版は「調査の方法」セクション、general版は導入部、academic版は方法論節。

## §9 出力アーキテクチャ

### 2層の原則

creation の出力は2つの層で構成される。

| 層 | ファイル種別 | 性格 | 配置先 |
|----|-----------|------|-------|
| **API層** | `.md`, `.yaml`, `.json` | 他のシステムからデータを取得するエンドポイント。APIのように機能する | `assets/creation/{kind}/{lang}/md/` |
| **配信層** | `.pdf` | 読者への最終出力。人間が読むもの | `assets/creation/{kind}/{lang}/pdf/` |

**API層のファイルはデータベースである。** Jekyll がページを生成するとき、スクリプトが一覧を作るとき、他の出力が参照するとき——全て API層のファイルを参照する。したがって:

- API層のファイルは安定したパスを持つ（頻繁に移動しない）
- API層のファイルは機械可読性を保つ（front matter、構造化データ）
- API層のファイルの変更は、参照元への影響を確認してから行う

**配信層のファイルは生成物である。** API層のファイルとルールから生成される。手で直接編集しない。

### 公開しない出力（creation-pjdhiro）

### 命名規則

```
{topic}-{subtopic}.{ext}
```

言語はディレクトリで分離するため、ファイル名には含めない。

> **廃止**: 旧命名 `issue62-domain-*` は廃止。新規生成・参照ともに `domain-*` 命名を使うこと。

| 要素 | 値 |
|------|----|
| topic | `creation`, `survey`, `domain` |
| subtopic | `general`, `academic`, `designer`, `status`, `domain-index`, `{id}-{name}-{audience}` |
| ext | `.md`, `.pdf`, `.json` |

### 対話ログの記録義務

対話中に判断されたものは、その対話の対象になっているディレクトリの中にコンテキストとして役立つ何らかの log として記録すること。

ルールだけでは「なぜそのルールか」が失われる（S17）。テストケースだけでは「なぜそのテストか」が失われる（S59）。コンテキストこそがアルゴリズムでありテスト文である。

記録先:
- ルールのナレッジログ（各ルールファイル末尾）
- 対象ディレクトリ内の `_log/` フォルダ
- Issue コメント（GitHub）

### 配管仕様の所在

Jekyll/HTML/PDF各出力への変換処理（front matter付与、data属性マッピング、pandocメタデータ等）は共通基盤ルールの範囲外。以下を参照:
