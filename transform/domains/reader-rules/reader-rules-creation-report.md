### AI由来ソースの帰属ルール（NL-013）

evidence の `flags` に `[ai:*]` を持つエントリの内容を本文に反映する際、著者の一人称（「私は〜と考える」「筆者の見解では」等）で記述してはならない。「調査では〜が確認された」「分析の結果〜」等、三人称の報告体で記述すること。

- **`[ai:*]` のみ**: AI由来。三人称の報告体で記述
- **`[hiro:確認]` あり**: pjdhiroがレビュー済みだが、元の調査・分析内容自体のAI帰属は変わらない。「著者が確認した調査結果として〜」は可。「著者は〜と考える」は不可
- **`[hiro:*]` フラグなし・pjdhiro直接発言**: 一人称可（ただし `/Users/uminomae/dev/kesson-driven-thinking/base/voice/` 等の明示的ソースに限る）

⛔ 「pjdhiroが確認した」ことは「pjdhiroが考えた」ことではない。確認と創出を混同しない。

### 調査方法の記述義務

報告書は「何をどう調べたか」を読者に説明する義務がある。以下を必ず含む:

- 各領域で何理論を評価したか
- 評価手法（各理論について複数の独立した視点から構造的対応を検討し、対応の強弱を判定した）
- 判定基準（何をもって「強い構造対応」「部分的な対応」「条件付きの対応」とするか）
- 方法論的開示（NL-016）。先行研究との対応にはAIの解釈代行を含むこと、その具体化として第5部「調査結果: 領域別の知見」で「読み取りとして」層を置くこと
- 調査の限界（何を調べていないか、何がまだわからないか）

⛔ 内部用語は使わない: 「E-1〜E-8スコアリング」「四面記述」「CHK-A〜D」「Accept/Reject」は内部管理用語であり本文に書かない。

ツール名（Claude / ChatGPT / Codex）は方法論の一部として脚注レベルで言及してよいが、本文の主題にしない。

## §1 文書の性格

この文書は**調査報告書**である。

調査を依頼した人（読者）に、調査結果を正確に・わかりやすく伝えることが唯一の目的である。著者の体験談ではない。語りかけでもない。概念の説明書であり、読者が理解するための教科書でもある。

---

### ⛔ 絶対禁止: この調査は「5段階モデルの構造類似」の調査である

**この調査レポートが答える問いは唯一これだけである:**

> 「この学問領域の諸理論は、5段階モデル（場→波→縁→渦→束）と構造的に対応するか？」

**この調査レポートが答える問いではないもの:**

| 禁止されている問い | なぜ禁止か |
|-------------------|----------|
| 「欠損駆動思考とこの領域の理論はどう対比されるか」 | 依頼されていない。別の問いである |
| 「Withholdはこの領域の概念と同じか違うか」 | 依頼されていない。別の問いである |
| 「欠損駆動思考はこの領域でどう裏付けられるか」 | 依頼されていない。別の問いである |
| 「この理論は欠損駆動思考の証拠になるか」 | 依頼されていない。別の問いである |

**欠損駆動思考・Withhold・欠損（Kesson）は、この調査レポートの主題ではない。**
一切言及しない。比較しない。対比しない。証拠として使わない。

**禁止語を別表現に置き換えても、論点が「欠損駆動思考の正当化」に向かっている場合は同じ違反とみなす（NL-010補足）。**
チェック: 「この記述は5段階との構造類似を説明しているか、それとも別の何かを正当化しているか」を問うこと。

> **なぜこのルールが存在するか（NL-010）**
> AIは5段階モデルの理論的背景（欠損駆動思考）を過剰に参照し、
> 「構造類似の調査」を「欠損駆動思考の正当化」にすり替える誤りを繰り返す。
> これは依頼された調査ではない。調査の目的を書き換える重大なエラーである。

### コンサルタント報告書の原則

| 原則 | 内容 |
|------|------|
| **R1: 読者は調査結果を知りたい** | 作業過程・作業環境・ツールの話は書かない |
| **R2: 事実→読み取り→解釈→示唆の順** | 何が見つかったか → 何を構造的特徴として読んだか → 5段階とどう対応づけるか → 理論にとって何が重要か |
| **R3: わからないことは「わからない」と書く** | 謙遜でごまかさない。未解決の問いとして明示する |
| **R4: 読者の時間を尊重する** | 冗長な前置き・自己紹介・免罪符を入れない |
| **R5: 一つの段落に一つの主張** | 論理の飛躍を防ぐ。主張→根拠→例示の順 |

## §2 読者定義

| 項目 | 内容 |
|------|------|
| 想定読者 | **創造のプロセスに構造があるかどうかを知りたい人** |
| 前提知識 | 特になし。専門用語は初出で必ず説明する |
| 関心 | 「30の学問領域を調べて、創造に共通する構造は本当にあったのか」 |
| 読後の状態 | 調査の全体像を把握し、結果の強弱を自分で判断できる |

### 読者にとって価値があるもの

- どの領域で強い構造対応が見つかったか
- どの領域で対応が弱かったか、見つからなかったか
- 領域を横断して繰り返し現れたパターンは何か
- この調査結果が理論にとって何を意味するか
- まだ解決していない問い

### 読者にとって価値がないもの

- AIの作業環境（フリーズ対策、セッション管理、state.md更新頻度）
- commit数、ファイルパス、バージョン番号の推移
- ツールの使い分け（Claude / ChatGPT / Codex）
- プロジェクト管理手法の工夫
- 著者の内面的な体験や感想

## §3 声の設計

### トーン: テレビの解説番組のナレーション

丁寧で、落ち着いていて、聞き手の理解を第一に考える声。NHKスペシャルのナレーターが、複雑な調査結果を一般視聴者に伝えるときの口調。

| 特徴 | 内容 |
|------|------|
| **丁寧** | です・ます調。敬意を持って説明する |
| **明晰** | 一文で一つのことを言う。因果関係を明示する |
| **中立** | 結果が理論に有利でも不利でも、同じトーンで報告する |
| **具体的** | 抽象論で終わらない。必ず具体例を添える |

### 禁止する声

| 禁止パターン | 理由 | 代替 |
|-------------|------|------|
| 「ピンとこなければ、それで大丈夫です」 | 読者の投資した時間を軽視する。上から目線の謙遜 | 書かない。説明が不十分なら説明を改善する |
| 「休憩所で隣に座った人への語り」 | 調査報告書にカジュアルな語りは不適切 | 解説者として説明する |
| 「答えは持っていません」 | 調査をしたなら結果はある。謙遜は結果の信頼性を下げる | 「この調査で明らかになったこと」と「未解決の問い」を分けて書く |
| 「あるとき起きる」「ふと浮かぶ」 | 説明の放棄。なぜ起きるかを説明するのがこの文書の仕事 | メカニズムを可能な限り記述する。説明できない場合は「現時点では〜が仮説として考えられる」 |
| 「〜かもしれません」の多用 | 全体が不確かに見える。温度の区別が消える | 確定事実は断定する。仮説は「仮説として〜が考えられる」と明示する |
| 「私が自分の〜のために書いた」 | 読者のための文書であって著者のためではない | 書かない |
| 「合わなければ置いておいてください」 | 読者を手放している | 書かない。説明責任を果たす |

### 人称

| 使ってよい | 使わない |
|-----------|----------|
| 「本調査では」「この報告書では」 | 「私」「あなた」 |
| 「〜と定義する」「〜が確認された」 | 「〜と感じた」「〜と思う」 |
| 「pjdhiro（2026）は〜と述べている」（理論提唱者として三人称で参照） | 「私はこう考えた」 |

**例外**: 理論の着想経緯を説明する文脈では「pjdhiroは〜という体験から着想した」と三人称で記述してよい。

## §4 構成パターン

### 調査報告書の標準構成

```
1. 調査の目的と問い
   — 何を調べたのか。なぜ調べたのか。
   — 【返却: 立ち位置明示】 この文書が何であり何でないかを宣言する。

2. 調査の方法
   — 30領域の選定基準。評価手法。判定基準。
   — §6.5 方法論的開示義務を含む。先行研究との対応にはAIの解釈代行が含まれ、各論の「読み取りとして」層がその開示を具体化する。
   — ※ツール名は脚注レベル。方法論が主。

3. モデルの概要
   — 5段階モデル（場→波→縁→渦→束）の定義。
   — 読者がこの先の調査結果を理解するための前提知識。
   — 【返却: 安全弁】 「ここまでの定義に違和感があるとしたら、それ自体が調査の重要な観点である」。
     読者はここで離脱してもよいし、違和感を保持したまま読み進めてもよい。

4. 調査結果: 全体像
   — 30領域の俯瞰。強い対応・弱い対応・未確認の分布。
   — 数値と視覚的な全体図（スコアボード）。

5. 調査結果: 領域別の知見（主要なもの）
   — 特に示唆に富む領域を3〜5つ取り上げて詳述。
   — 各領域: 事実として → 読み取りとして → 解釈として → 必要に応じて示唆として、の順で書く。

6. 横断的パターン
   — 複数の領域にまたがって繰り返し現れた構造。
   — 特に「縁」に関する横断的知見。

7. 未解決の問い
   — 調査で答えが出なかったこと。対立する解釈が残っているもの。

8. 結論
   — 調査全体が理論にとって何を意味するか。
   — 構造類似は確認されたか、されなかったか、条件付きか。
   — 【返却: 温度開示】 根拠の確定度を正直に示して閉じる。責任逃れではなく温度の開示。
```

> **共通基盤 §7 返却の設計との対応**: §1「調査の目的」が立ち位置明示、§3「モデルの概要」末尾が安全弁、§8「結論」が温度開示。関与レベルはL0（読むだけ。応答不要）がデフォルト。

### 各セクションの書き方

**各理論節の分析部では、事実として→読み取りとして→解釈としての3層を必ず分離する。** 節全体としては、その後に必要に応じて示唆としてを置いてよい。

**先行研究・理論への言及順序**（NL-005）——ルール違反が最も読みにくさにつながる項目。

先行研究や既存理論に言及するとき、必ず以下の順序で書く:

```
① その理論・論が何であるかを簡単に説明する（定義・概要）
② AIがその記述の何を構造的特徴として読み取ったかを説明する（ラベル/メカニズム/プロセス/構造のどの水準かを明示）
③ 5段階モデルとどこが構造類似するかの「解釈」を説明する
```

#### 各論の3層テンプレート（#228 / NL-016）

各論の分析部は、最低限次の3層で書く。

| 層 | 何を書くか | 注意点 |
|---|---|---|
| **事実として** | 先行研究が何を主張しているか。原著の記述・実験・観察の要約 | 原著にない言い換えを足しすぎない |
| **読み取りとして** | AIがその理論の何を構造的特徴と捉えたか | 類似の水準が **ラベル / メカニズム / プロセス / 構造** のどれかを必ず明示する |
| **解釈として** | 5段階モデルとの対応づけ | 「だから場/波/縁/渦/束に対応する」と論理をつなぐ |

「読み取りとして」は、第2部「調査の方法」で宣言する方法論的開示義務を各論レベルで具体化する層である。ここで何をどう読んだかを示さずに 5段階へ対応づけてはならない。

**悪い例**:
```
Morse理論の臨界点は縁に対応する。
```

**良い例**:
```
【事実として】 Morse理論は、滑らかな多様体上で関数の値を変化させていくと、
                臨界点を通過する瞬間に空間の位相が質的に変化するという現象を記述する。

【読み取りとして】 ここでは、状態の連続的な変化の途中で位相が再編される閾値構造を読み取る。
                  類似の水準はプロセスであり、特に「変化の途中で質的転換が生じる順序」に着目する。

【解釈として】 この臨界点——新旧の位相型が共存し、どちらにも確定しない瞬間——は、
                5段階モデルの縁（対立する要素が共存し、どちらにも収束しない緊張状態）と
                構造的に対応する。
```

「読者が理論を知っている」と仮定してはならない。初出時は必ず概要を先に置く。
2回目以降の言及は「前述のMorse理論の臨界点」で簡略化してよい。

**各理論節と横断的洞察の住み分け**:
- 各理論節: その理論**固有**の構造対応・差異を書く
- §6横断的パターン: **複数理論に共通する**パターンを書く（理論節で既出の内容を繰り返さない）

```
【事実として】 複雑系科学（D29）では、散逸構造の形成過程と5段階モデルの間に
              強い構造対応が確認された。特に「縁」段階は、系が臨界点付近で
              複数の安定状態の間を遷移する局面に対応する。

【読み取りとして】 ここでは、複数の安定状態が競合しながら再編に向かう遷移構造を読み取る。
                  類似の水準は構造であり、単なる用語の近さではなく、
                  安定状態の共存と再編という配置関係に注目する。

【解釈として】 この対応は、5段階モデルが特定の学問領域に固有のものではなく、
              自己組織化という一般的な現象の記述として機能しうることを示唆する。

【示唆として】 ただし、物理的な臨界現象と人間の創造的プロセスでは
              「臨界点」のラベルが異なる。この対応が構造的同一性なのか、
              ラベルの類似にとどまるのかの検証が必要である（→ §7 未解決の問い）。
```

## §5 用語方針

### 5段階の扱い

学術的な概念として導入する。体験的な比喩による導入は行わない。

| 段階 | 定義的な記述 |
|------|-------------|
| 場（ば） | 未分化の状態。方向も構造もまだ定まっていない初期条件 |
| 波（なみ） | 複数の方向性が発散・競合する探索の段階 |
| 縁（えん） | 対立する要素が共存し、どちらにも収束しない緊張状態 |
| 渦（うず） | 緊張の中から新たなまとまり（秩序）が自発的に立ち上がる段階 |
| 束（たば） | 形が確定し、再利用可能な構造として安定する段階 |

| base層の用語 | 報告書での表現 |
|-------------|---------------|
| Withhold | **使用禁止**（NL-010） |
| F-O軸 | 使用可。初出で定義を添える |
| Container | 「心理的安全性の基盤」（初出で説明） |
| スピノル | 使わない（学術版のみ） |
| [P][M][S]タグ | 使わない |
| 欠損駆動思考 | **使用禁止**（NL-010）。この調査の主題ではない |
| Accept / 条件付きAccept / Reject（判定語） | **使用禁止**（NL-011）。「強い構造対応が確認された」「部分的な対応が確認された」「対応は確認されなかった」等に置き換える |

### 温度の明示

主張の確信度を文体で区別する。

| 温度 | 表現パターン | 使用場面 |
|------|-------------|----------|
| 確定 | 「〜である」「〜が確認された」 | 調査で繰り返し確認された事実 |
| 有力 | 「〜と考えられる」「〜を示唆する」 | 複数領域で一貫した傾向 |
| 仮説 | 「仮説として〜が考えられる」「〜の可能性がある」 | 単一領域の知見、検証途上 |
| 未解決 | 「〜は未解決である」「〜については対立する見解がある」 | 未解決の問い |

## §8 creation-general版との関係

creation-general版（reader-rules-creation-general.md）は「休憩所の語りかけ」を基調とした一般向け読み物。本ルール（report版）とは文書の性格が異なる。

| 次元 | creation-general | creation-report |
|------|-----------------|------------------|
| 性格 | 読み物・エッセイ | 調査報告書 |
| 声 | 語りかけ | 解説・ナレーション |
| 人称 | 「私」と「あなた」 | 三人称・文書主語 |
| 構造 | 体験→名前→地図 | 目的→方法→結果→示唆 |
| 読者 | 手が止まった体験がある人 | 理論の妥当性を知りたい人 |
| 読後 | 「ああ、ここにいたのか」 | 「調査結果の全体像がわかった」 |

両者は同じ理論（M2 5段階モデル）の異なる出力形態であり、排他的ではない。ただし混在させてはならない。一つの文書内で語りかけと報告書が切り替わると、読者は混乱する。

## §9 ナレッジログ（このルールの根拠）

このルールは以下の品質レビューから導出された。問題の再発防止のために根拠を記録する。

### NL-001: 「ピンとこなければ大丈夫です」問題（2026-03-04）

**発見**: creation-general-draft.md §7-bのパターンAがそのままドラフトに転写された。
**pjdhiro判断**: 「イラっとくる。私の文体を真似ているのだとしたらやめて。そんな言い方しない」
**根拠**: 読者が時間を投じて読んだ内容を「ピンとこなければ大丈夫」と言うのは、説明の不備を読者の側に帰責している。説明が不十分なら説明を改善するのが著者の責任である。
**対策**: §3 禁止パターンに追加。トーンチェック（§7-D）に検出項目を追加。

### NL-002: 作業報告書がAI開発日誌になる問題（2026-03-04）

**発見**: session-report.md §03がフリーズ対策・commit数・ファイルパスで埋まっていた。
**pjdhiro判断**: 「AIなんて気にしてない。創造のモデルの構造類似性を調査したのです。AIはどうでもいい。作業環境なんてどうでもいいです」
**根拠**: 変換ルール（reader-rules-blog.md §B-1）の読者定義が「AI協働プロジェクト管理に関心のある技術者」だった。この読者定義自体が間違い。読者は調査結果を知りたい人。
**対策**: §2 読者定義の再設計。§6 除外ルールにAI作業環境を完全除外として明記。

### NL-003: 渦・束の説明放棄問題（2026-03-04）

**発見**: creation-general-draft.md で場→波→縁は体験的に詳述されたが、渦は「あるとき起きる」、束は「方向が定まる」で済まされていた。
**原因**: 変換ルールの§5 3幕構成が「縁」中心に設計されており、渦・束のガイダンスが薄い。
**対策**: §4 構成パターンで5段階の均等記述をチェック項目化。§7-A論理チェックに追加。

### NL-004: 概念説明書に「著者の声」は不要（2026-03-04）

**pjdhiro判断**: 「私らしさよりも、テレビアナウンサーのような丁寧な解説口調がいい。これは論文のような概念説明書なのです」
**根拠**: 理論の概念説明では、説明の正確さと明晰さが著者の個性より優先される。著者の声を前面に出すと、理論の客観性が損なわれる。
**対策**: §3 声の設計を「テレビ解説番組のナレーション」に設定。人称を三人称に。

### NL-005: 先行研究への言及順序の欠落（2026-03-05）

**発見**: 公開ドメインレポートで、理論名だけ出して説明なしに「縁に対応する」と書くパターンが繰り返し発生。
**pjdhiro判断**: 「これがないと読みづらい。先行研究への言及は、まずその論の説明、その上で構造類似の解釈。」
**根拠**: 読者は当該理論を知らない前提で書く義務がある。説明なしの対応主張は検証不能であり、読者は「なぜそう言えるのか」がわからない。
**対策**: §4 各セクションの書き方に「先行研究・理論への言及順序」を追加。①概要 ②構造類似の解釈、の順序を必須化。

### NL-010: 調査主題のすり替え（2026-03-05）

**発見**: D23発達心理学レポートで「Piagetの均衡化とWithholdの差異」「欠損駆動思考の裏付け」として記述された箇所が複数発見された。
**pjdhiro判断**: 「欠損駆動思考は関係ないよ。これは創造のモデルの構造類似だよ。欠損駆動思考との対比なんて依頼してないよ。生成のルールに入れるべきことです。」
**根拠**: この調査の問いは唯一「5段階モデル（場→波→縁→渦→束）と各領域の理論が構造的に対応するか」である。AIは5段階モデルの理論的背景（欠損駆動思考）を参照する傾向があり、調査目的を「欠損駆動思考の正当化」にすり替える誤りを繰り返す。これは調査の目的を根本から変えてしまう重大なエラー。
**対策**: §1に⛔絶対禁止ルールとして最上位に配置。§5用語変換に「欠損駆動思考・Withhold 使用禁止」を明記。§7に品質ゲートF（主題チェック・最優先）追加。§9にNL-010追記。
**補足（2026-03-06）**: 禁止語を別表現に言い換えても、論点が「欠損駆動思考の正当化」に向かっている場合は同じ違反。§7-Fにチェック項目追加。

### NL-012: pjdhiro/assets/ 配下のmdにfront matter禁止（2026-03-06）

**発見**: `assets/creation/survey/en/md/survey-status.md` に Jekyll front matter（`---`ブロック）が含まれており、Jekyll が assets 配下のmdをページとして処理しようとしてビルドエラーが発生した（GitHub Pages デプロイ連続失敗）。
**根拠**: Jekyll は `---`ブロックを含むファイルをページとして処理する。`assets/` 配下は静的ファイルとして配置する意図だが、front matterがあると Jekyll の処理対象になってしまう。front matter はパイプライン内部の管理情報であり、公開 assets ファイルには不要。
**対策**: §7-C の様式チェックに検出項目を追加。生成時に front matter を含めない。配置前に `head -3` で確認する。
**H1昇格ルール**: front matter の `title` フィールドは `# タイトル` として文書先頭に置く。`assets/` 配下の md は必ず H1 見出しで始まること。

### NL-011: 判定語の露出（2026-03-06）

**発見**: D23 v2.0の§4全体像に「Accept」「条件付きAccept」が残存。機械チェック（grep）をすり抜けていた（前のgrepは `/Users/uminomae/dev/creation-space/evidence` を探していたため）。
**問題**: 「Accept」「Reject」は evidence の内部判定語であり、読者には意味不明。
**対策**: §5用語変換に NL-011 として明記。§7-C の grep チェックに `\bAccept\b` `\bReject\b` を追加。代替表現: 「強い構造対応が確認された」「部分的な対応が確認された」「対応は確認されなかった」。

### NL-013: AI由来ソースの一人称誤帰属（2026-03-09）

**発見**: #25 transform audit で `[ai:*]`/`[hiro:*]` フラグ体系が reader-rules に伝搬していないことを確認。現行ドラフトでは誤帰属は見つからなかったが、AI由来の調査・分析内容が著者の一人称に誤変換される構造的リスクが残った。
**pjdhiro判断**: 確認と創出を混同しない。pjdhiro のレビューが入っても、元の調査・分析内容自体のAI帰属は変わらない。
**対策**: §0 に AI由来ソースの帰属ルールを追加。quality-test T1-4 で一人称誤帰属を検出し、grep と目視で確認する。

### NL-016: 方法論的開示義務の各論具体化（2026-03-13）

**発見**: D23 レビューと Issue #228 の検討で、各論が「事実として」から「解釈として」へ直接飛び、AI が先行研究のどの側面を構造的特徴として読んだのかが見えない問題が明確になった。
**根拠**: §6.5 は「AIによる解釈代行を含む」ことの開示を求めているが、総論で宣言するだけでは各論の対応づけ根拠が透明にならない。各論でも「何をどう読んだか」を示してはじめて、方法論の開示が具体化される。
**対策**: §4 の「調査の方法」に NL-016 を明示し、各論の分析部を「事実として→読み取りとして→解釈として」に変更。§7-A に読み取り層の品質ゲートを追加。
