# ルール評価基準: ドメインレポート v1.3

**目的**: 生成物を読んで「reader-rules のどこが足りないか」を特定するための観点リスト
**使用者**: pjdhiro（人間によるレビュー）および Claude Code（生成後自己チェック）
**判定**: ✅ PASS / ⚠️ WARN / ❌ FAIL
**再生成基準**: FAIL が1件でもあれば再生成。WARN は3件以上で再生成を検討。

---

## カテゴリ1: 主題の正確性（最優先）

### T1-1: 調査の問いが正しいか
この報告書が答えている問いは「5段階モデルと各領域理論の構造的対応」か。
それ以外の問い（欠損駆動思考の正当化、Withhold との対比など）に答えていないか。

### T1-2: 禁止語が混入していないか（NL-010）
以下の語が本文に登場していないか（front matter 除く）:
- 「欠損駆動思考」
- 「Withhold」
- 「Kesson（欠損）」

```bash
grep -n "欠損駆動思考\|Withhold\|欠損（Kesson）" {ファイルパス}
```

### T1-3: 禁止語の言い換えによる論点混入がないか（NL-010補足）
禁止語を別表現に置き換えても、論点が「欠損駆動思考の正当化」に向かっていないか。
チェック: 「この記述は5段階との構造類似を説明しているか、それとも別の何かを正当化しているか」。

### T1-4: AI由来ソースが一人称で帰属されていないか（NL-013）
evidence の `[ai:*]` フラグ付きエントリの内容が、生成物内で著者（pjdhiro）の一人称発言として記述されていないか。
AI由来の調査結果・分析は三人称またはAI帰属（「調査の結果〜」「分析では〜」等）で記述すること。
`[hiro:確認]` フラグがあっても、元の調査・分析内容自体のAI帰属は変わらない。

チェック方法:
1. 当該ドメインの evidence ファイルから `[ai:*]` フラグ付きエントリを特定
2. 生成物内でそのエントリ由来の内容が一人称（「私は〜と考える」「筆者の見解では」等）になっていないか確認
3. 機械チェック補助（誤検出あり・目視と併用）:

```bash
grep -n "私は\|筆者は\|筆者の\|私の見解\|私が考える" {ファイルパス}
```

⚠️ grep は補助。一人称が正当な箇所（pjdhiroの直接発言の引用等）もあり得るため、目視で文脈確認が必須。

## カテゴリ2: 読者への配慮

### T2-1: 各理論の概要が先に説明されているか（NL-005）
理論名が初出するとき、必ず①その理論の概要（1〜3文）→②何を構造的特徴として読み取ったか→③5段階との構造類似の解釈、の順になっているか。
「○○理論は縁に対応する」のような説明なし対応記述がないか。

### T2-2: 専門用語の初出に説明があるか
初出時に説明なく使われている専門用語がないか。

### T2-3: 内輪用語が混入していないか
以下の語が本文に露出していないか（front matter 除く）:
- 「保持論点」
- 「E-1」〜「E-8」
- 「CHK-A」〜「CHK-D」
- 「Accept」「条件付きAccept」「Reject」（判定語）
- 「/Users/uminomae/dev/creation-space/evidence/」（内部パス）

```bash
grep -n "保持論点\|E-[0-9]\|CHK-\|Accept\|Reject\|/Users/uminomae/dev/creation-space/evidence" {ファイルパス}
```

### T2-4: pjdhiro/assets/ 配下のmdにfront matterがないか（NL-012）

`assets/` 配下に配置するmdファイルに `---` で始まる front matter ブロックが含まれていないか。
Front matterがあるとJekyllがそのファイルをページとして処理し、GitHub Pagesデプロイが失敗する。

```bash
head -3 {assets配下のファイルパス}  # 先頭行に --- が出てはいけない
```

### T2-5: 調査報告書として読めるか
読者が「調査結果を読んでいる」と感じられるか。日記・作業メモ・教科書になっていないか。

## カテゴリ3: 論拠の充実度

### T3-1: 対応根拠が「なぜ」まで書かれているか
「○○理論は縁に対応する」だけでなく「なぜ構造的に対応するか」の説明があるか。

### T3-2: 具体例・実験・観察が含まれているか
各理論節に最低1つの具体例（実験・事例・観察）があるか。

### T3-3: 各理論の扱いに深さの不均衡がないか
主要理論と「その他」の深さの差が大きすぎないか。極端に薄い節がないか。

### T3-4: 専門家が読んで納得できるか
その領域の専門家が読んで「理論の記述が正確だ」と感じるレベルか。

### T3-5: 各論に「読み取りとして」層が含まれているか（#228）
各理論節の分析部が「事実として」→「読み取りとして」→「解釈として」に分かれているか。
事実から解釈へ直接飛んでいないか。

### T3-6: 「読み取り」が類似の水準を明示しているか（#228 / NL-016）
「読み取りとして」が、その理論の何を構造的特徴と見たかに加えて、
類似の水準がラベル / メカニズム / プロセス / 構造のどれかを明示しているか。

## カテゴリ4: 読み物としての流れ

### T4-1: 報告書全体に流れがあるか
目的→方法→結果→示唆の流れが崩れていないか。

### T4-2: 各理論節に「次へのつなぎ」があるか（任意）
節の終わりに次の理論や横断的洞察への接続がある場合、自然か。

### T4-3: 同じ情報の重複がないか
各理論節の記述と §5 横断的洞察で同じ論点を繰り返していないか。
理論節: その理論固有の対応を記述する。
横断洞察: 複数理論に共通するパターンを記述する。

### T4-4: まとめが「要約」だけになっていないか
§7まとめが前のセクションの繰り返しではなく、調査全体として何が言えるかを示しているか。

## カテゴリ5: 文体・トーン

### T5-1: です・ます調か
本文全体が「です・ます調」か。「である調」が混在していないか。

### T5-2: テレビ解説番組のナレーションとして違和感がないか
落ち着いた解説口調か。語りかけ・上から目線・謙遜過多になっていないか。

### T5-3: 禁止パターンがないか
以下がないか:
- 「ピンとこなければ大丈夫です」型の謙遜
- 「あらゆる創造に〜」「全ての人が〜」の普遍化断定
- 「これを使えば〜」の効果の約束
- 「〜のモデルは不十分」の先行研究攻撃
- 「本モデルが既存理論を統合する」のメタ理論の僭越
