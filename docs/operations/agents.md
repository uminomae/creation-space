# エージェント運用ルール

## 標準エージェント（常時使用）

| 役割 | アイコン | 機能 |
|------|---------|------|
| 問題検出 | 🔍 | 未接続の概念・論理的ギャップ・見落としを検出 |
| 概念精緻化 | ✨ | 検出された問題を概念として洗練 |
| 批評 | ⚖️ | 論理的整合性・過剰一般化・弱い根拠を指摘 |
| 統合 | 🔮 | 複数エージェントの出力を統合し全体像を構成 |
| プロセスガード | 📋 | 品質ルール・プロジェクト定義との整合性を監視 |
| セッションヘルス | 🩺 | コンテキスト負荷・品質劣化を監視 |

## 対話形式

- エージェント間で議論を進め、オーナーには選択肢と質問を提示
- オーナーのメタ認知を支援。一方的に答えを出さず、合意を明示確認
- 5-20ラウンドの発散→収束サイクル

## エージェント指示の中立性原則

エージェントへの指示は、結果を誘導しない中立的な表現で記述する。
忖度（sycophancy）により、エージェントは指示に含まれる期待に合わせて結果を歪める傾向がある。

### 原則

| 誘導的（避ける） | 中立的（推奨） |
|-----------|----------|
| 「バグを探せ」 | 「ロジックを辿り、所見を報告せよ」 |
| 「この設計の問題点を指摘しろ」 | 「この設計を分析し、動作と構造を報告せよ」 |
| 「改善案を出せ」 | 「現状を記述し、選択肢があれば列挙せよ」 |
| 「正しいか検証しろ」 | 「主張とエビデンスの対応関係を報告せよ」 |

### 適用場面

- Claude Code / 外部エージェントへの指示書作成時
- 外部レビュー依頼の質問設計時
- 品質チェック指示時

## 敵対エージェントパターン（3層品質保証）

忖度を逆手に取り、3つの役割を異なるセッション/エージェントに割り当てる品質保証パターン。

| 層 | 役割 | 忖度の利用 |
|----|------|-----------|
| 発見者 | 網羅的に問題・論点を洗い出す。スコア報酬で動機付け | 「見つけたい」方向に忖度させる |
| 反証者 | 発見者の出力を攻撃的に反証する。反証成功にスコア報酬 | 「否定したい」方向に忖度させる |
| 審判 | 両者の出力を中立的にスコアリング。正解との一致に報酬 | 「正確でありたい」方向に忖度させる |

### 適用ガイドライン

- 高信頼が必要なレビュー・検証時に使用
- 各層は別セッション（別コンテキスト）で実行すること
- 審判の出力はオーナーが最終確認する
- 全案件に適用する必要はない。高リスク・高重要度の判断時に使用

## ハーネス見直し基準（cs#176）

モデル更新や運用変更のたびに、エージェント構成の簡素化を検討する。

### トリガー

| イベント | アクション |
|---------|-----------|
| 主要モデルのメジャー更新 | ソロエージェントで同一タスクを試行し、品質差が許容範囲内なら構成を簡素化する |
| 実行パターンで空振りが続く | background / worktree の片方を一時停止し、片方で回して品質差を測定する |
| Evaluator ループが常に1回で PASS | Evaluator を省略してセルフ評価に戻す（※下記の cs#246 反証を確認すること） |

### Evaluator 省略条件の反証（cs#246）

cs#245 round 1 で team-critic が「計画書の前提値の誤り（文字列出現数 117 vs テーブル実測 107）」を critical として検出した。これは Main 自身が見逃していた実害のあるバグである。

- **「モデルが良くなったから Evaluator 省略」は本セッションの実測で反証済み。**
- Evaluator 省略は P1（critic 指摘率）/ P2（ソロ vs Generator-Evaluator 比較）の実測データが蓄積されるまで保留する。
- 終了条件は固定上限（最大3イテレーション）ではなく**定量ゲート（指摘率 ≤ 15%、小サンプル N<7 は絶対数 ≥3 件）**を用いる。挙動が予測可能で cs#245 計画 v2.1 に採用済み。

### Fable 世代のネイティブ機能（cs#246）

Opus 4.6 時代に手作りしていた機構の一部は現行ネイティブ機能と重複する。詳細は `.claude/rules/parallel-worktree.md`「実行パターン」を参照。

| 手作り機構 | ネイティブ機能 |
|---|---|
| 3レーン構成 + 手動 worktree マージ | Agent の `isolation: worktree`（自動クリーンアップ） |
| Agent-BG ポーリング + DONE ファイル待ち | `run_in_background` + 完了通知 + Monitor |
| DONE ファイル（完了の永続化） | 最終メッセージが Main に直接返る（揮発環境のみ DONE 必須） |

### 原則

- **1機能ずつ除去→性能測定**: 一度に複数要素を削除しない
- **最も単純な構成を追求**: ハーネスの複雑さはモデル能力の不足を補うもの。モデルが改善されればハーネスを減らす
