# CL-008: 原典取得は「わかったつもり」で間違える — url-verified は取得可・同定済を意味しない

**日付**: 2026-06-21
**関連Issue**: cs#250（cs#221・cs#240 の教訓統合）

## 何が起きたか

cs#249（source-note backfill）で原典取得を進めたところ、過去数ヶ月で繰り返してきた失敗を**また**再発見した:

1. `access_status: url-verified` の URL を LLM（WebFetch/curl）で取得しようとして大半が失敗（MDPI/Nature/PNAS/Wiley/SAGE/figshare/philpapers 等が Akamai/Atypon の 403/402、archive.org 等はスキャンPDFで `pdftotext` 不可）。
2. OA URL が **別論文を返した**: D23-S08 Luyckx 2008 の URL（`repository.uantwerpen.be/.../d:irua:19968`）が Luyckx 2023 の別論文を返した。気づかなければ誤論文から source-note を生成していた。

決定的に問題なのは、**これらはすべて既に文書化済み**だったこと:
- cs#221（CLOSED）が「url-verified と LLM 可読性のズレ」を失敗パターンごと列挙済み
- cs#240（OPEN・未実装）が「raw-confirmed 化時の書誌クロスチェック」を D03-S08 教訓として提案済み

## 原因分析

1. **教訓が CLOSED issue に埋もれ、取得作業の開始時に必ず読む正本に infuse されていない**。だから毎セッション、同じ崖から落ちる。
2. `access_status` の意味が正直でない。`url-verified` は「人間がブラウザで見えた」だけなのに「取得できる」と誤読される。検証主体（人間ブラウザ）と読解主体（LLM）の能力差が status に表現されていない。
3. 書誌クロスチェック（取得PDF＝manifest の論文か）が手動・省略可能で、構造的に漏れる。

## 対策

1. `url-verified` は「取得可能」を意味しないと正本に明記。LLM 取得経路の成功/失敗ホスト類型を表で正本化（**ブロック先を同じ方法で何度も叩かない**）。
2. source-note 生成前に **書誌クロスチェック必須**（`pdftotext`/`pdfinfo` で著者・年・タイトル・DOI を抽出 → manifest 照合 → 不一致なら停止＋起票）。
3. エスカレーション経路を明記（手動DL→raw-confirmed / スキャンは OCR=Read ビジョン / 誤URLは manifest 起票）。
4. **再発防止の本丸**: 上記を CLOSED issue ではなく「取得作業の入口で必ず読む正本」に置き、READING-PROTOCOL から参照する。
